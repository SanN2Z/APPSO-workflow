# DeepSeek Harness 的内测窄门：它可能在找一组「故障探针」

看到那张内测邀请，我第一反应也很接近 LinearUncle 的玩笑：我也想现场搭一个。让 Fable 5 跑一小时，一个能启动的 Agent 仓库也许真能出现。可邀请的报名门槛随即把这股冲动按住了：申请者得是 Agent Harness 相关开源项目开发者，还要附上 GitHub ID 和开源代表作。

这道窄门更像在收集测试仪器。每位真正做过 Harness 的开发者，都带着一套由自身工程取舍校准过的故障视角。把他们放进同一次内测，DeepSeek 收到的就可能不只是更多次试用，而是同一个系统被不同方向探测后留下的截面。

这个判断也让时间点显得有意思。邀请出现的前一天，DeepSeek-V4-Flash-0731 官方模型卡已经把待发布的 DeepSeek Harness 写进 Code Agent 评测脚注。一个尚未公开形态的系统，先在评测条件里露面，又把测试入口对准做过同类东西的人。此时最值得追问的，正是这些同行能看见普通体验者不容易说清的什么。

## 每套 Harness，都训练出一种故障直觉

Agent 真正执行任务时，模型外面还有一圈运行框架：它组织上下文，接入工具，限制命令，处理失败和重试，再判断任务是否完成。每一处都要做选择，而一种选择往往会放大某类故障。

长期处理上下文的人，看到 Agent 中途跑偏，可能先查信息在哪一步被截断或污染；做工具链的人，会追问调用参数、返回值和状态有没有传错；收紧过权限的人，更容易发现系统为了完成任务悄悄跨过了边界；被重试循环折腾过的人，会留意 Agent 是否只是在重复同一条失败路径；做过验收的人，则会追问一句「完成了」究竟由回复、文件、测试还是别的证据支持。

这些都只是可能的经验类型，并不意味着某位申请者已经入选，更不代表 DeepSeek Harness 会采用哪种架构。它们的价值在于，同一个现象可以被多套故障假设照亮。普通体验者说「这里不好用」，做过框架的人更可能接着问：错误从哪一层开始，沿着哪条路径扩散，换一种取舍又会付出什么代价。

GitHub ID 和开源代表作因而提供了一层筛选信号。公开仓库不能自动证明一个人适合内测，却至少能让测试方看到他实际实现过哪些取舍，而不是只听一段自我描述。DeepSeek 官方的 awesome-deepseek-agent 仓库本就收录 Claude Code、Codex、OpenCode、Pi、Hermes、LobeHub 等多种接入指南；团队并不陌生于同一模型进入不同外层工作流的情形。现在，自研 Harness 成了被观察的一方，来自不同框架的经验便可能充当一组方向各异的探针。

## 探针扎下去，被测对象才露出轮廓

模型卡给了一个很窄、但很实在的窗口：公开基准中的 Code Agent 任务使用 DeepSeek Harness minimal mode，同时指定 max reasoning effort、temperature 1.0 和 top_p 0.95。模型卡跑分不能算独立复现，也无法拆出 Harness 单独贡献了多少；这些条件反而提醒我们，一次 Agent 表现是模型与外层运行方式共同作用的结果。

于是，同一项任务如果换一种上下文组织方式就失败，问题可能指向隐藏的输入假设；接上另一套工具协议才出错，可能暴露接口边界；权限变严便卡死，说明执行路径依赖了什么；重试次数增加仍原地打转，则能逼出恢复机制的缺口。这里列举的是测试思路，不是已经发生在 DeepSeek Harness 上的故障。

不同探针给出的结果甚至可能相互冲突。有人会主张保留更多上下文，有人担心噪声随之进入；有人希望工具权限更宽，有人把可控性摆在前面。冲突本身也有信息：它迫使测试团队看见「修好」背后的代价，而不是把所有反馈都归成一个待办列表。

如果这次定向邀请意在获得高质量 bug，这样的同行组合很合理；它也可能兼有架构比较或人才发现的考虑。公开信息没有测试协议，无法确认真实动机，也没有给出产品形态、正式发布日期、价格、是否开源，以及它是否只做 Coding Agent。边界虽多，却不妨碍我们理解这张门票在筛选哪种信息。

## 一份高信号反馈，怎样从「它坏了」长出来

假设一个 Agent 修改完代码后宣布任务完成，结果测试没有通过。低信号反馈停在「它失败了」和一张报错截图。高信号反馈会把故障重新走一遍：固定任务输入与必要配置，保留执行轨迹，指出上下文在哪一步变化、哪次工具调用返回了什么、权限拦截后系统如何转向、重试是否重复旧路径，以及最终验收为什么放过了错误结果。

接下来还要把观察与判断分开。轨迹里实际发生了什么是一层；「可能是上下文组装造成的」是另一层。再附上最小复现、预期结果和一个可比较的替代方案，维护者才有机会复现、定位，并决定是否值得承担修复的代价。增加上下文可能带来噪声，放宽权限会增加风险，延长重试会增加耗时，更严格的验收也可能误拒绝正确结果。能把这些取舍一并说清，反馈才真正变得可执行。它还要求测试者知道，什么证据足以让另一位工程师重现同一故障。

这正是开源代表作可能带来的信息增量：它不保证作者一定判断正确，却让对方有机会证明自己能从异常走到证据，再从证据走到可讨论的工程选择。对想展示 Agent 项目的人，这也比继续堆功能更具体。挑一个真实或可复现的失败，交代输入、轨迹、分层判断、修复方案与回归验证；首页只能证明项目曾经跑起来，这条链才证明你知道怎样检验它是否完成了任务。

再回到那句「我也想现场搭一个」。一个小时或许足够生成仓库骨架，甚至搭出一个最小复现和记录轨迹的入口；它不会自动附赠一枚校准好的故障探针。你仍得知道往哪里扎，怎样区分模型、Harness 与工具的问题，又怎样把异常写成别人可以复现和处理的反馈。真要用好这一小时，最有分量的成果未必是一套看起来完整的新 Agent，而是一条短、尖锐、从故障直达证据的测试链。
