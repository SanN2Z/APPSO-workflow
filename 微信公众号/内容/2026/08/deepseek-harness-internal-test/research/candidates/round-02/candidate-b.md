# DeepSeek Harness 开内测，Fable 5 现搭一个还来得及吗？

## 点开报名条件，我的仓库名白想了

我是在一张很懂 AI 圈笑点的转发截图里，看到 DeepSeek Harness 开始招募内测的。

LinearUncle 转发了团队成员 Tianyi Cui 的帖子，大意是：准备让 Fable 5 花一个小时，现场搭一套出来赶报名。

这个玩笑好笑，是因为它没有离现实太远。现在看着 AI 新建仓库、补齐文件，再把一个 Demo 跑起来，一个小时已经不算特别夸张。我甚至顺手替这个临时项目想了几个仓库名。

![LinearUncle 转发招募帖，并拿 Fable 5 现场搭项目开玩笑](assets/x-linearuncle-fable5-joke.png)

然后我点开了原帖。

Tianyi Cui 邀请的对象，是做过 Agent Harness 相关开源项目的开发者。报名要交 GitHub ID，还要附上自己的开源代表作；有兴趣的人可以回复帖子或私信联系。

没有「现场做一个也算」，也没有专门给新仓库留的入口。至少从提交项看，对方想看的，是一个有公开来路、经得起翻记录的项目。

我的仓库名白想了。可这道门槛反而留下一个谜：AI 都能临时搭项目了，为什么内测还盯着那些慢吞吞做出来的旧作品？

## 这套 Harness 还没发布，已经先替 V4 跑过分

按通常的顺序，我们应该先等产品发布，再看它能做什么。但我把招募帖放到一边，倒回 DeepSeek-V4-Flash-0731 的官方模型卡，顺序突然反了过来。

模型卡写明，公开的 Code Agent 任务使用了尚待发布的 DeepSeek Harness minimal mode。

也就是说，这套 Harness 还没有正式亮相，已经先出现在 V4 的评测现场。招募帖看起来像故事的开头，模型卡却告诉我们：戏其实演到中场了。

![DeepSeek Harness 公开信号时间线](assets/timeline-harness-public-signals.png)

这里得压住一个很容易顺手滑过去的结论。模型卡中的结果属于厂商自报，不能据此把 V4 的成绩归功于 Harness，本文也不拿它继续做跑分比较。它能确认的只有一件事：这不是一张刚画出来的产品概念图，至少 minimal mode 已被用于公开 Code Agent 任务。

普通人可以先把 Harness 理解成模型干活时坐进去的工作台：它把文件、终端、任务进度和结果检查接在一起。模型会写代码之后，还得有人把「去哪里动手、做到哪一步、怎样算交付」串起来，这套工作台就在管这件事。

![Harness 把模型与真实任务所需工具接起来](assets/harness-system-stack.png)

现在仍然不知道它最终长什么样、何时发布、如何定价、是否开源，测试协议也没有公开。于是，眼下最具体的产品信号，反倒不是功能表，而是 DeepSeek 正在找什么样的人来试它。

## 一个小时能搭出 Demo，搭不出「踩坑史」

再回头看 Fable 5 的玩笑，问题已经从「能不能搭」变成了「搭完拿什么去测」。

假设它用一个小时做出任务面板：按钮能点，基础测试能过，README 也写得很漂亮。把它塞进一个带着旧依赖、历史脚本和奇怪目录的真实项目，隐藏问题才可能冒头。维护过这类项目的人会知道，某个看似多余的兼容分支为什么不能删，也见过一次修复怎样撞坏另一处功能。最后还得补上回归检查，证明同一个坑没有换件衣服再回来。

一小时可以生成代码和结果，生成不了这段可信的前因后果。

一个长期维护的开源项目，留下的不只是文件数量。Issue 里有失败现场，提交记录里有改法，测试里藏着作者最怕再次发生的事；有时还会留下回滚，承认上一次判断走错了。这些记录让别人看见：问题怎么被发现，方案为什么改变，修完以后怎样确认它真的可靠。

当然，仓库年纪大不自动等于作品好，提交次数多也可能只是热闹。真正有用的是那条能追溯的判断链。临时 Demo 可以证明「现在能跑」，旧项目更有机会回答「遇到麻烦以后还跑不跑得住」。

当生成代码越来越快，代表作的分量也会悄悄换位置。漂亮骨架会越来越便宜，项目撞过哪些墙、为什么选了这条修法，以及作者有没有办法验证结果，反而更难临时补齐。

## DeepSeek 找来的，可能是一群专业拆台的人

我把报名条件倒着读了一遍：既然 Harness 已经能陪 V4 走过标准化的 Code Agent 任务，接下来最缺的，未必是再看一次漂亮演示。它更需要有人把工作台拖进各自积灰的仓库，让旧测试、旧依赖和旧毛病一起上场。

做过同类开源项目的人，通常已经习惯了这种找茬方式。他们会追问结果能不能复现，会拿一次成功去撞另一种环境，也会在工具说「完成」之后继续检查产物。真有问题，他们交回来的不只是一句「不好用」，还可能包含出错步骤、影响范围和验证办法。

![开源开发者把 Harness 放进真实项目里挑问题](assets/doodle-open-source-builders-test.png)

所以，我更愿意把这轮定向邀请理解成一次「专业拆台」招募：找一群手里有旧项目、脑中有事故记录的人，去试着让新工作台露出破绽。

这仍是作者判断。DeepSeek 没有公开解释筛选动机；为了获得高质量 bug、覆盖更多兼容情况，或者顺手发现人才，都说得通。在产品和测试协议尚未公布时，我们最多只能确认，公开作品给了团队一条较快的路径，找到那些已经在真实项目里摔过跤的人。

那么，Fable 5 现在搭一个还来得及吗？加入这场玩笑，一个小时当然够；拿它去换这张内测门票，从公开条件看还差一段没法伪造的过去。除非它顺便把时间机器也搭了。

代码变快了，经历不能快进。
