# 正文初读

A 的主旨很快成立：先用「为什么门票发给造过东西的人」设问，再把 Harness 解释为模型外层的运行框架，最后收束到「同行更可能找出框架在哪里会坏」。合上文章后，我能复述出它的两层结论：门槛可能是在筛选有故障定位经验的测试者；这次邀请仍不能说明产品形态、发布时间、价格或是否开源。

B 也能让普通读者准确复述这两层结论，而且阅读中的因果路径更显眼：「模型会答」不等于「任务会完成」，所以内测必须分辨模型问题与运行层问题；要做这种分辨，就更需要做过同类系统的人。它对「目前不能说明什么」的收口同样明确，并把「内测」「发布」「开源」三个状态分开了。

两篇都具备公共价值。A 更紧，结尾的边界清单尤其稳；B 更容易让读者用一条因果链记住答案。

# 必要顺序与删节测试

最强连接出现在 B：前一段提出内测需要检查上下文、工具调用、失败恢复和结果验收，下一段随即用「这也解释了」追问为什么报名材料是 GitHub ID 与开源代表作。后一段确实像被前一段的问题逼出来，因为它回答的是「谁有能力定位这些层级的问题」。A 从 Harness 定义到「做过 Harness 的开发者会继续追问哪一层出错」也很顺，但随后关于开源项目经验分散的段落更像补充佐证，推进感稍弱。

交换测试：若把 B 中「模型卡已经露出这层系统」与紧随其后的「于是，内测要回答的不只是模型聪不聪明」两段互换，「于是」会先于具体证据出现，而模型卡条件则沦为事后补证；原来的「材料证据 → 测试问题 → 测试者门槛」顺序明显更必要。这个交换对 B 的损伤大于 A 中多数相邻段落互换所造成的损伤。

材料取舍方面，A 略胜。两篇都敢舍弃具体跑分，也都没有罗列项目名称；A 把第三方项目压成四类经验，B 多展开了一层子 Agent、沙箱与工作台，但这些细节仍服务于「经验不雷同」，不算离题。

- A 最可删除的一段：以「这个动作还有一层有限的对照」开头、并列外部 Harness 接入指南与部门招聘的段落。它能补背景，却不是回答报名门槛所必需。

- B 最可删除的一段：以「这次邀请不是孤立动作」开头、串联招聘、外部接入指南和自研 Harness 的段落。删去后，核心因果链与事实边界仍完整。

# 事实、推断与未知项回忆

## A

- 事实 1：8 月 1 日，Tianyi Cui 邀请做过 Agent Harness 开源项目的开发者参加内测，申请需附 GitHub ID 和代表作。
- 事实 2：7 月 31 日的官方模型卡称公开 Code Agent 任务用了 DeepSeek Harness minimal mode，并把 Harness 标为「to be released」。
- 作者推断：先找做过同类系统的人，一个合理目的可能是更快暴露运行框架的问题。
- 未知项：DeepSeek Harness 是否会开源。

## B

- 事实 1：6 月 21 日，Tianyi Cui 称 DeepSeek Harness 是新成立的部门，并在招聘研究员、工程师和产品经理。
- 事实 2：DeepSeek 官方仓库此前收录了 Claude Code、Codex、OpenCode 等外部 Agent 或编程助手的接入指南。
- 作者推断：要求公开代表作，可能便于从公开产物判断申请者能否定位系统层故障并提供复现路径。
- 未知项：DeepSeek Harness 是否只服务 Coding Agent。

# 事实护栏

A 未触发重大事实阻断项：没有把厂商自报写成第三方结论；明确指出「to be released」不等于已经开源；产品名、界面、日期、价格、人数和协议均保留为未知；第三方项目只用于说明经验类型；没有使用 LinearUncle 玩笑。需要留意的一处轻微硬化是结尾的「这轮邀请说明，DeepSeek 当前需要的反馈……还包括这套框架在哪里会坏」：前文已把这一点标为合理推断，但这里的陈述语气比证据所能直接支持的更确定。它尚不足以构成重大阻断。

B 未触发重大事实阻断项：厂商自报与可复现性边界清楚；「to be released」、内测和公开发布没有混同；未补写产品细节；明确说明第三方项目不代表报名、入选或 DeepSeek 产品形态；招募动机始终用「推断」「可能」和「不足以确认」限定；没有使用 LinearUncle 玩笑。其「独立工程」是对部门招聘、模型卡披露和内测邀请的综合解释，并未被扩写成独立商业产品的既成事实。

# 选择

选择：B

信心：中

B 更好地把模型卡中的 Harness 条件变成「内测究竟要排查哪一层」这一读者问题，再让 GitHub ID 与开源代表作自然成为答案，完成了更清楚的「材料 → 问题 → 门槛」阅读路径。
