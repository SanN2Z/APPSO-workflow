# DeepSeek 自研 Harness 开内测，为什么先找「同行」？

8 月 1 日，DeepSeek 团队成员 Tianyi Cui 公开邀请一批特殊测试者：做过 Agent Harness 相关开源项目的开发者。申请时不只留个联系方式，还要附上 GitHub ID 和开源代表作。

这不像一张面向普通用户的候补登记表。产品细节尚未公布，DeepSeek 先找的却是最可能拆解、质疑甚至重做同类系统的人。为什么？答案大概藏在 Harness 到底负责什么。

## 模型会答，不等于任务会完成

可以把 Harness 理解为模型外面的运行系统。模型负责生成和推理，Harness 决定给它哪些上下文、记忆和工具，允许执行什么命令，失败后怎样重试，最后又由什么标准验收。它不是一种固定产品，而是一组会直接改变 Agent 表现的工程选择。

DeepSeek 7 月 31 日发布的 DeepSeek-V4-Flash-0731 模型卡，已经露出了这层系统：公开 Code Agent 任务使用了 DeepSeek Harness minimal mode，并指定 max reasoning effort、temperature 1.0 和 top_p 0.95；Harness 的状态仍是「to be released」。模型卡中的 Agent 跑分是厂商自报，也是在这些条件下得到的，不能直接理解为模型脱离 Harness 后仍会原样复现。

于是，内测要回答的就不只是「模型聪不聪明」，还有更棘手的问题：上下文会不会丢，工具调用能否收住，失败能否恢复，结果是否真的验收过。

## 懂得怎么坏的人，才容易测出问题

这也解释了 GitHub ID 和开源代表作为什么会成为报名材料。公开项目显示，Harness 开发者处理的问题跨度很大：有人研究记忆和自我改进，有人做系统级观测，有人编排子 Agent、记忆与沙箱，也有人搭建多 Agent 的组织和调度工作台。这些项目并不代表已经报名或入选，更不代表 DeepSeek 将做成其中任何一种形态；它们只说明这群人带来的经验并不雷同。

基于这些信息，一个较克制的推断是：DeepSeek 想要的可能不是一批只会报告「好不好用」的体验者，而是能定位「哪一层出了错」、给出复现路径，并识别框架取舍的专业反馈者。要求开源代表作，还让这种能力至少有公开产物可供判断。当然，邀请也可能兼有生态摸底、寻找合作对象等目的，现有材料不足以确认动机。

## 信号已经出现，产品仍在雾里

这次邀请不是孤立动作。6 月 21 日，Tianyi Cui 曾称 DeepSeek Harness 是新成立的部门，正在招聘研究员、工程师和产品经理。DeepSeek 官方仓库此前也已收录 Claude Code、Codex、OpenCode 等外部 Agent 与编程助手的接入指南，走过「让模型进入别人的 Harness」这条路。如今模型卡出现自研 Harness，随后又邀请同类开源开发者内测，至少说明 DeepSeek 正把模型外层的运行系统当作一项独立工程来建设，并开始寻求外部专业反馈。

但信号只能读到这里。内测邀请不等于产品发布，「to be released」也不等于已经开源。截至 8 月 2 日，正式产品名、界面、发布日期、价格、开放方式、首批人数和测试协议均未公开，甚至无法确认它是否只服务 Coding Agent。现在最值得记住的，不是 DeepSeek 已经做出了怎样的产品，而是它选择让最懂 Harness 难点的人，先来检验这个尚未揭面的系统。
