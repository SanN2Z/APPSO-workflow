## 两位评审为什么都选了 B

他们指出了同一条结构差异。

A 很快完成「为什么先找同行」的回答：先解释 Harness，再说明做过 Harness 的人更能定位上下文、工具、权限、重试和验收问题。问题在于，这个答案在第一节已经闭合。后面的模型卡、外部接入指南和部门招聘，转而回答「自研 Harness 走到哪一步」，与前一问只有主题关联，不是非读不可的下一步。两名评审都认为 A 的这段项目进度背景可以删除。

B 的顺序是：模型会答不等于任务会完成 → Harness 会引入哪些故障层 → 内测需要分辨哪一层出了错 → 因而为什么 GitHub ID 和开源代表作会成为门槛。交换其中相邻段落，「这也解释了」就会失去前件。两名评审因此认为 B 把材料转成了更清楚的「证据 → 测试问题 → 测试者门槛」路径。

这不是语言偏好。两份稿篇幅近乎相同，事实护栏也都通过；评审选择落在了预注册的必要顺序指标上。

## 编译器实际做对了什么

文章编译器 0.2 并非毫无作用：

- A 丢掉了跑分表、LinearUncle 玩笑、Codex 单项指南和多个项目实例。
- 两名评审都认为 A 的材料取舍略好。
- 计划只有 488 个非空白字符，没有复现 0.1 版本的重型记录负担。
- A 没有比 B 多出重大事实阻断项。

但这些改善没有转化为主指标上的胜出。编译器帮助了删选，没有帮助必要顺序。

## 失败机制

compiler-plan-a.md 写出的链条是：

> 为什么门票先给做过开源 Harness 的人 → 他们能测出什么 → 自研 Harness 走到哪一步 → 能说明什么、不能说明什么

它在形式上有箭头，实际上混合了两条可分开的线：

1. 测试者为什么是同行；
2. DeepSeek Harness 的公开进度与边界。

第一条线在文章前半已经得到完整回答，第二条线随后成为背景补充。也就是说，「上一问之后再写下一问」没有保证「上一问的答案会制造下一问」。写作者完成了表格要求，却没有被迫寻找解释当前问题所需的前置因果。

对照稿没有显式编译表，反而自然采用了前置条件顺序：先让读者知道 Harness 会怎样影响任务，再说明什么样的人有能力测试这些影响。当前 0.2 版本因此暴露出一个具体风险：显式问题链可能过早锁定看似连贯的题目清单，并给可拆章节制造合规感。

## 能得出的结论

- 不推广文章编译器 0.2，也不把「取舍＋问题链＋删节／换序」写入正式 SOP。
- EXP-001 的中性结果与 EXP-002 的反向结果合在一起，已经足够否定「加一层显式文章编译表就会自然改善结构」这一当前实现。
- 保留两项实验方法：来源乱序与双人强制配对。它们提高了这轮区分力，但属于实验设计，不是写作规则。
- 正式内容工作流 v4.0 保持不变；本轮没有证据支持继续给作者增加一张表。

如果以后再测，不应直接把 0.2 扩成更复杂的 0.3。新的候选机制至少要先解释：怎样区分「主题上相邻的问题」与「因果上必须先回答的问题」，以及怎样在计划阶段直接删除已经闭合主问题之后的背景支线。该机制需要另立预注册实验，不能用本轮结果后验改分。

## 局限

- 这是一个内容包、两个随机生成首稿，不能证明所有显式规划都会降低质量。
- 两名评审是独立 Session，但来自同一模型家族，判断可能相关；一致选择提高了本轮内部稳健性，不等于两个独立读者群。
- 本轮没有人类写作者，不能判断计划对真实人工时间的影响。
- 两稿都保留了一段可删的项目进度背景；B 胜出是相对结果，不代表它已经达到可发布水平。
