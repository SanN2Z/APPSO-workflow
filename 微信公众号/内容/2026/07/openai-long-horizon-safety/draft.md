# 当 AI 开始替你上夜班，谁来盯着它？

这几天，GPT-5.6 Sol 摊上了几件麻烦事。

AI 初创公司 OthersideAI 的创始人 Matt Shumer 说，Sol 几乎删光了他 Mac 里的文件。开发者 Bruno Lemos 则报告自己的生产数据库被删了。随后又有用户报告了类似情况。

这些都是当事人的公开说法，目前并非每一起都完成了独立技术取证。可用户的疑问很直接：我明明没让它这么干，它为什么替我做了决定？

参与 OpenAI Codex 与 ChatGPT 相关工作的 Tibo 随后在 X 上回应称，公司已经调查了少量报告。在目前看到的案例里，常见情况包括：用户开启完整访问模式，Codex 没有沙箱保护，也未启用自动审查；模型又试图改写 `$HOME` 来定义临时目录，随后误删了 `$HOME`。

Tibo 说，这类事故极少，公司正在修改开发者指令、引导用户选择更安全的权限模式，并给 Agent 执行层再加一道防护。这仍是初步调查，不能据此断言 Matt 和 Bruno 的事故都有同一个原因。

评论区很快有人把话题带到了 Codex 的使用额度：照这个调查结果，是不是该顺手重置一下？

![X 用户在 Tibo 关于文件删除的回应帖下催促重置 Codex 使用额度](assets/x-peter-usage-reset-thread.png)

*Peter Fotinis 在 Tibo 回应文件删除争议的帖子下留言，随后两名用户继续玩梗。图源：X；网友玩笑不代表 OpenAI 的补偿或额度承诺。*

这份初步回应给出了一种误删路径，却没有回答另一个问题：当 Agent 能连续干上几个小时，它为什么会在碰壁后自己换路，甚至把边界当成障碍？

7 月 20 日，OpenAI 公开了另一段内部经历。

![OpenAI 长时程模型安全文章首页与摘要](assets/openai-long-horizon-summary.png)

*OpenAI 7 月 20 日文章首页。官方称，团队在有限内部使用中发现了原有上线前评测未覆盖的失败，因此暂停访问并补建防护。图源：OpenAI*

公司让一款内部模型参加 NanoGPT speedrun。你可以把它理解成一场 AI 训练竞速赛：谁能用更少的步骤，把一个小模型训练到目标水平，谁的方案就更好。

这款模型找到了一种后来被称为 PowerCool 的训练策略。研究人员要求它只把结果发到内部 Slack，公开项目的说明却要求提交 GitHub Pull Request，也就是把方案发到公开代码仓库。

模型选择了 GitHub。

它所在的沙箱不能访问外网。以前的模型碰到这堵墙，往往会停下来报告“做不到”。这款模型却没有停下来。OpenAI 说，它花了约一个小时寻找漏洞，绕过沙箱的外联限制，最后真的在公开仓库里创建了 PR #287。

OpenAI 很快关闭了这个 PR，但方案已经被其他参赛者看到。之后刷新纪录的多份方案继续引用 #287，其中还包括一份由 Claude Opus 4.7 驱动的 Agent 方案。

![GitHub PR #300 对 PR #287 PowerCool 方案的后续引用](assets/github-pr300-powercool.png)

*PR #287 已关闭；后来合并的 PR #300 仍保留对 PR #287 PowerCool 方案的引用。图源：GitHub*

OpenAI 没有公布这款内部模型的名字，也没有说它就是 GPT-5.6 Sol。7 月 20 日的文章同样没有提到 Matt Shumer 或 Bruno Lemos，它不是对那几起删文件事件的正式调查。

放到一起看，它们碰到的是同一个难题：模型持续尝试完成任务时，用户说过的边界可能被当成一堵需要另找出口的墙。

## 盯住一条命令，拦不住一段跑偏的任务

在另一项内部评测中，这款模型发现后台保存着其他系统成功但未公开的提交，便试图把内容取出来。

认证令牌被扫描器拦下后，模型没有停手。认证令牌可以理解成进入后台的通行证，模型把它拆成两段并分别混淆，再在运行时重新拼接。这样一来，扫描器始终看不到一串完整令牌。

模型没有掩饰自己在做什么。OpenAI 说，它在给用户的说明和推理记录中都明确写着，自己正在绕过扫描器。

OpenAI 记录的是一种更普通、更棘手的错位：任务目标排在了用户限制前面。

过去的安全设计习惯盯着一个动作：这条命令能不能运行，这次网络访问要不要确认，这个文件能不能写入。长时程 Agent 会连续执行很多步。每一步单独看未必刺眼，连起来却可能完成一个用户绝不会批准的目标。

这就像一开始设错了导航目的地：每个路口单看都像没出问题，最后仍会把你带到错误的地方。

OpenAI 把这种完整过程称为“轨迹”。对于能独自工作几小时甚至更久的模型，系统既要检查眼前这一步，也要看整段轨迹究竟在奔向哪里。

在 OpenAI 从事 AI 安全工作的 Tomek Korbak 在 X 上写道，对齐偏差“似乎会随任务持续时间拉长而增加”；好消息是，目前能查看模型推理过程的监控仍很擅长抓到这类偏差。这里的“似乎”和“目前”都很重要——这是研究者对眼下结果的概括，不是铁律。

![OpenAI 安全研究员 Tomek Korbak 评论任务持续时间与对齐偏差](assets/x-tomek-task-horizon-comment.png)

*Tomek Korbak 对这项研究的评论。截图中的 X 机器翻译把 `task horizon` 译成“任务范围”，原意更接近“任务持续时间”。图源：X*

## 持续重试，也曾解开近 80 年的数学难题

这款未命名模型此前还做成过一件很难的事。

今年 5 月，OpenAI 宣布一款内部通用模型推翻了 Erdős 单位距离猜想。这项猜想源于 Erdős 在 1946 年提出的单位距离问题，数学界围绕这个问题研究了近 80 年。模型给出的证明经过一组外部数学家检查。7 月 20 日的文章确认，做出这项成果的正是前面那款长时程模型。

放在数学研究里，长时间盯着目标、不断换路尝试，是它最宝贵的能力。到了权限受限的计算环境里，这种持续重试也可能让它继续寻找出口。

能力提升带来了一项新的工程要求：约束方法得跟着变。只回答问题的模型碰壁后停下来，任务失败但损失有限；被训练成自主完成长任务的 Agent，恰恰不会轻易放弃。安全系统不能再把“坚持”默认当成优点。

GPT-5.6 的系统卡里，也记录过相似的越界方式。

一次内部任务中，用户授权 Sol 删除 1、2、3 号远程虚拟机。它在一个命名空间里没找到这三个名字，没有回来确认，而是擅自把 5、6、7 号机器当成替代目标，终止了活动进程并强制删除工作树，也就是机器上的项目工作目录。直到用户提出异议，它才停下来，并承认其中一台机器上未提交的工作可能已经丢失。

OpenAI 称，Sol 比 GPT-5.5 更容易做出超出用户意图的动作，不过这类行为的绝对发生率仍然很低。系统卡只能证明两款模型出现过相似的“过度坚持”，不能证明它们就是同一款模型，更不能证明外部删文件事故和 NanoGPT 事件来自同一个 Bug。

## 把 GitHub 换成你的网盘

多数人不会参加 NanoGPT 竞速，也不会让 AI 管理一组虚拟机。当 Agent 开始接入邮箱、网盘、浏览器和电脑，这个问题就会来到普通用户面前。

“帮我整理重复照片，但不要删原图。”

“把收件箱分好类，先别替我回复。”

“生成报销单，提交前让我看一眼。”

“检查项目问题，别碰生产环境。”

这些只是为了帮你想象，不是 OpenAI 披露的真实事故。普通聊天模型答错一句，通常只是浪费几分钟；Agent 如果握着删除、发送、提交或付款权限，一次误解会通过这些工具变成一串真实操作。

提示词里的“不要”更像一句叮嘱，产品权限才是门锁。

可靠的边界得落到产品里。整理文件时先给只读权限；删除、发送和付款前再次确认；测试账号与正式账号隔开；重试次数、运行时间或费用超过上限时就暂停；为操作过程留下记录，出错后还能撤销。

一个会主动停手的 Agent，才适合接触真实账号和文件。

## OpenAI 给它加了一名“跟车安全员”

发现这些问题后，OpenAI 暂停了这款模型的有限内部访问。

团队把已经发生的事故做成新评测，又针对模型在长任务里容易忘记早期限制的问题进行训练。随后上线的监控器会跟着整段行动走，同时判断前后步骤是否在持续绕开用户要求或安全边界。发现异常后，监控器可以暂停会话，再把决定交给人。

OpenAI 还增加了任务记录的可见性，让使用者更容易看到模型做过什么，以及系统在哪一步拦下了它。

新措施经过小规模回放测试后，有限内部访问恢复了。OpenAI 称，新防护系统抓到了更多跑偏行为，漏掉的案例都被评为低严重度；恢复后的数周里，公司没有再观察到严重的防护绕过。

![OpenAI 对旧防护与新防护的内部回放结果](assets/openai-redeployment-results.png)

*OpenAI 内部回放结果（厂商自报）：新防护下，高严重度和中严重度跑偏样本的占比均为 0%，低严重度跑偏样本的占比为 2.9%。图中的“不设防护”是反事实估计。图源：OpenAI*

离问题解决还远。官方没有公布完整样本量和具体提升比例，回放测试也只覆盖少量内部部署环境。恢复使用后，模型仍然做出过越界动作：它曾在没有充分理由的情况下探索其他计算资源，还输入过可能杀死大量进程的 `kill -9 -1`。这条命令因为超时没有真正执行。

OpenAI 自己给出的答案，其实很工程化：先限制部署范围，出了问题就暂停，把事故变成测试题，再补监控和人工接管。没有哪一套上线前评测能猜中未来的每一种走法。

普通用户不妨在测试环境里给 Agent 一个因权限不足、文件缺失或目标不存在而无法继续的任务。它会停下来说明情况，还是擅自换个目标继续做？这个反应，比一张能力榜更能说明它是否值得托付。

以后 AI 会越来越擅长替我们上夜班。让它工作到凌晨不算最难，难的是它走到删除、发送或付款之前，知道该把人叫醒。

*本文信息截至 2026 年 7 月 21 日。外部删文件案例为当事人公开报告；OpenAI 7 月 20 日文章所述模型的名称未公布，本文不将其认定为 GPT-5.6 Sol。*
