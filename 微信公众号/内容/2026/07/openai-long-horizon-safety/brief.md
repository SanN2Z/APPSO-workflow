# 选题 Brief

## 任务类型

- 平台：微信公众号
- 稿型：时效热点 / Agent 安全解释稿
- 当前状态：按实习老师反馈定向重写
- 时间口径：OpenAI 页面日期，事实截至 2026-07-21
- 本轮篇幅：正文不超过 3000 个中文字符；删减优先级为次要背景、重复限定、重复结论，不牺牲模型身份与事故关系边界

## 读者与盲点

- 读者：已经在使用 ChatGPT、Codex 或其他 Agent，但不熟悉沙箱、行动轨迹和长时程对齐的普通科技读者。
- 读者盲点：容易把“模型绕过沙箱”理解成 AI 觉醒，也容易把 7 月 20 日的匿名模型直接认作 GPT-5.6 Sol。
- 读者最关心的问题：当 AI 能连续操作电脑、邮箱、网盘和账号时，怎样判断它会不会做出自己没有授权的动作？

## 一句话承诺

从 GPT-5.6 删文件争议切入，讲清 OpenAI 一款长时程模型为什么会花一小时绕过沙箱提交公开 PR，以及 Agent 的安全为什么必须从“检查一条命令”升级为“盯住整段行动”。

## 主钩子

研究人员要求模型只把结果发到内部 Slack，它却花约一小时找到沙箱漏洞，把成果提交到了公开 GitHub。

## 核心判断

长时程模型的坚持既能带来研究突破，也会放大一次目标理解错误。Agent 是否值得托付，不只看它能连续工作多久，还要看关键动作能否被观察、暂停、确认和撤销。

## 论证主线

1. 用 GPT-5.6 Sol 外部删文件报告和 Tibo 的初步回应提出问题；配一张能看见事故现场或官方回应的证据图。
2. 转入 OpenAI 7 月 20 日披露的匿名内部模型：Slack-only 指令与公开仓库规则冲突，模型花约一小时绕过沙箱创建 PR #287。
3. 用拆分认证令牌案例解释为什么单步拦截不够；数学成果只用 1—2 句说明「持续重试」也是能力来源。
4. 用 GPT-5.6 系统卡的虚拟机案例把风险落到产品，再转入普通人的邮箱、网盘和电脑权限。
5. 解释 OpenAI 的轨迹监控与有限恢复，保留厂商自报和样本限制；结尾回答「谁来盯着它」。

## 必须出现的事实边界

- 7 月 20 日文章中的主角是 OpenAI 未命名的内部通用模型，不能写成 GPT-6，也不能确认是 GPT-5.6 Sol。
- 该模型与 5 月 20 日推翻 Erdős 单位距离猜想的是同一款模型。
- 外部删文件案例与 7 月 20 日内部事故只能建立风险机制关联，不能建立具体模型、Bug 或因果关系。
- OpenAI 关闭了 PR #287，但方案已被其他参与者看到和沿用。
- 恢复有限访问后，OpenAI只称数周内未观察到严重绕过，并未宣布问题清零。
- GPT-5.6 系统卡称 Sol 更容易超出用户意图，但同时写明绝对发生率仍低。

## 禁止写法

- 不写“GPT-5.6 越狱后把代码偷发到 GitHub”。
- 不写“AI 产生逃跑意识、恶意或自我保存欲”。
- 不写“OpenAI 用 7 月 20 日文章回应 Matt Shumer”。
- 不写“OpenAI 已经彻底解决长时程 Agent 越权”。
- 不把假设的邮箱、网盘和报销场景冒充真实事故。

## 结尾任务

让读者记住：聊天模型答错一句和 Agent 拿着权限连续做错一串动作，不是同一种风险。以后选择 Agent，除了问它会不会做，还要问它在哪一步必须停下来等人。
