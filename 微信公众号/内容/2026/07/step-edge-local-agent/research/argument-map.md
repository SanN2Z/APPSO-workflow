# 论证图

## 一句话因果链

```text
Agent 要在手机上持续办事
        ↓
高频感知与小动作不能每一步都等云端
        ↓
本地模型承接看、听、定位、调用；云端承接复杂推理
        ↓
胜负从单模型跑分转向端云路由、系统权限、设备耐力和失败恢复
```

## 证据映射

| 模块 | 人话问题 | 证据 | 限制 / 反例 | 读者后果 |
|---|---|---|---|---|
| 当日事件 | 今天到底发布了什么 | Step Edge 官方页、IT之家时间 | 媒体主要转述官方 | 先确认不是旧闻 |
| 本地必要性 | 为什么不能所有步骤都发到云端 | Step Edge、Apple、Android 官方文档 | 本地模型能力与设备资源有限 | 理解低延迟、离线、隐私、成本 |
| 闭环 | “会聊”与“会办事”差在哪 | GUI 定位、工具调用、AppFunctions / ADK | 跨应用执行仍受系统权限约束 | 看发布会时先找执行与核验 |
| 端云路由 | 本地和云端谁替代谁 | Step Edge“简单本地、复杂上云”、Android Hybrid | 路由错误可能泄露数据或拖慢体验 | 关注何时上云、是否提示 |
| 安全恢复 | Agent 点错了怎么办 | 本文产品判断；Apple/Google 安全设计背景 | Step Edge 本轮资料尚未给出完整机制 | 付款、发送、删除前必须可确认与撤销 |
| 实机耐力 | 跑得动和长期好用是否一回事 | 官方推理速度页 | 缺少统一功耗、发热、兼容机型与第三方测试 | 暂不把架构发布写成体验成熟 |

## 最强反方

“Apple、Google 早就在做端侧模型和工具调用，Step Edge 没有新东西。”

回应：本文不主张技术首创。值得写的是，一个中国模型厂商在同一天把视觉、语音、GUI 执行、图像生成和端云协同打成一套端侧产品叙事，这说明竞争焦点已从“手机接一个云端聊天 API”向系统级闭环移动。是否做成，仍需实机验证。

## 不能跳过的桥

- 本地更快，不等于整条任务一定更快；需要区分单次 toolcall、模型预填充与完整任务。
- 数据本地处理更有隐私优势，不等于复杂任务上云时天然安全；要看路由和告知。
- GUI Benchmark 高，不等于真实 App 更新后仍稳定；要看环境变化、确认机制和失败恢复。
- 模型能力强，不等于手机能长期运行；功耗、发热、内存和 NPU 适配都是产品门槛。
