- 公司完整终稿按 `restricted` 处理，不复制进 Git。本文件只保存脱敏机制、短例证和可执行检查。
- 本轮只分析编辑变化，不据此宣布终稿的事实、图片权利和逐句语法已经通过。

## 结论

这轮不是简单「把句子改口语」，而是把一篇按来源依次汇报的分析稿，改成由一个普通读者问题驱动的叙事：公司开始测量 AI 使用和单人产出后，会不会不再招聘原本的「第二个人」？

核心变化有四层：

1. 开头从日期和新闻概述改成读者会立刻代入的问题，事实仍在首屏补齐。
2. 亚马逊、GitHub 和失业率不再各自形成一份小报告，而是依次回答「项目为何被重排—效率如何被看见—岗位为何可能不再出现」。
3. 大量只承担报告脚手架的清单、概念定义和三点式总结被减少；必要的产品分类继续保留，其余改成管理者、员工与求职者能看见的动作和场景。
4. 结尾只兑现「公司还会不会招第二个人」，不再临时增加一套个人竞争力方法论。

## 叙述调整

### 1. 从来源顺序改成读者追问顺序

内部第三版的章节基本对应材料来源：亚马逊、GitHub、宏观研究、DeepSeek 对照。终稿改成一条问题链：

```text
连做 AI 的人都被裁，学 AI 还有用吗
→ 公司保留的是 AI 标签，还是具体项目结果
→ 管理者如何看见 AI 使用深度与单人产出
→ 为什么失业率仍然平稳
→ 失业率漏掉了哪些从未发布的岗位
→ 谁会先感到招聘入口收窄
→ 公司还会不会招「第二个人」
```

检验方法不是数小标题，而是暂时隐藏小标题：线性论证要能说明为什么下一段现在出现；平行证据要共享明确的比较问题或尺度。两者都没有时，顺序仍然任意。

### 2. 从概念说明改成角色与决策

- GitHub 看板不再先被定义成「采用率和研发效能看板」，而是先说明它不是给程序员本人看的，而是给管理员和组织负责人看的。
- 「AI 采用成熟度」被翻译成可见动作：很少使用、主要补全、把任务交给 Agent、进入多 Agent 协作。
- 「劳动力需求下降」被翻译成管理者在下一份招聘申请上问：现有员工配合 AI 能不能先顶住。
- 「青年就业受影响」被翻译成新人原本用来入行的查资料、整理表格、简单代码和初版方案。

叙述因此不再悬在术语层，而是让读者看到谁观察、谁判断、谁不再招聘。

### 3. 先给官方边界，再做作者推断

终稿明确保留三道边界：

- GitHub 看板不是程序员能力评级，官方用途是观察采用、安排培训和判断采购效果。
- 亚马逊裁员不能证明这些员工被 AI 直接替掉。
- 22—25 岁结果只是早期信号，不能排除利率和疫情后招聘调整。

有了边界，作者才继续推断「使用深度与人均产出出现在同一张表里，可能改变团队人数基线」。这比把事实、厂商用途和作者判断揉成一句更稳。

还有两处证据收紧值得单独记录：

- 内部第三版写「同一天」，终稿改为「几乎同时」，避免用未经精确核对的同期关系制造两条新闻之间的强联系。
- 内部第三版声称管理者能看到「用在哪个项目」和「工作流发生了哪些变化」；终稿删除这层较强表述，只保留官方可见的采用阶段与并列指标。

### 4. 用「看不见的缺席」解释宏观数据

终稿没有继续抽象解释统计口径，而是写一支 10 人团队离开 2 人后不补招。没有发生新的裁员动作，团队编制却仍然少了 2 个岗位。

这个场景把「职位空缺减少不会立刻进入失业率」变成读者可以复述的机制。它是本稿的高价值叙述选择，但 10 人与 2 人只是说明场景，不得写成真实行业比例。

### 5. 用职业阶梯替代公司战略支线

内部第三版加入 DeepSeek 与亚马逊的 AGI 取舍对照，能解释同一技术标签为何产生不同组织动作，但也会把文章带向公司战略。终稿删掉这条支线，换成新人如何从基础任务入行，把论证重新拉回「谁最早失去招聘机会」。

可泛化机制是删掉不能继续推进唯一读者问题的高质量支线；DeepSeek 是否出现、青年就业是否出现都属于本稿选材。

### 6. 让事实句、判断句和短后果句承担不同节奏

终稿用独立短句完成转向、否定误读或压住结论，长段则承担事实、变量和限制。短句不是随机打散长度，而是在语义换挡处出现。

本稿确认的声音调度包括：

- 事实高密度段之后，用一条独立短句切换观察尺度；
- 口语只落在作者判断、具体动作或直接后果上，不均匀铺满每节；
- 同类框架词不扎堆，强对比句留给题眼，不让中段每隔几段都重新「揭示真相」。

### 7. 结尾停止另开方法论

内部第三版已经完成「从未收到录用通知」的情绪落点，随后又增加「是否在公司主线、能否让系统更快更稳」等个人方法。终稿把结尾重新压回标题问题，只保留一个读者后果：如果公司越来越不招第二个相似的人，AI 已经改变就业，只是失业率还没有完整记录。

个人建议不是不能写；只有 brief 从一开始就承诺行动指南时，结尾才应交付方法。观点稿不能在最后 10% 临时换题。

## 用户确认的 APPSO 冷静分析型声音约束

这些约束进入 APPSO 项目 adapter，不升级成所有中文写作的万能公式：

1. 结构稳定后再选择约 4—5 个口语落点；这是编辑靶点，不是必须凑齐的字数指标。每处都必须承担判断、动作或后果。
2. 独立短句只放在转向、纠偏、对比或结论处；不为制造人味随机切碎句子。
3. 「翻译一下就是」按 APPSO 本地约定禁用；不得机械替换成另一句套话。「说白了」可以保留 0—1 次，前提是它确实压缩了复杂判断。
4. 「严格来说」默认最多保留 1 处；「奇怪的是」「有意思的是」等同类框架词不得在相邻段落或相邻小节扎堆。
5. 高显著的「不是 A，而是 B」默认不预留。文章确有核心区分时，全篇集中保留不超过 1—2 处；也可以完全不用。中段若只是为了节奏重复，改成直接陈述。真实的逻辑排除、术语消歧和来源原话不按字面计数误杀。
6. 结尾回答开头承诺，不另起一套个人建议、检查清单或宏大结论；brief 明确承诺方法稿时除外。

## 不应从终稿机械学习

- 不把「第二个人」复制成其他就业稿的固定意象。
- 不规定所有新闻稿都必须问题开头；事实明确、篇幅很短的快讯可以直接交代事件。
- 不规定每篇都出现 4—5 个俗语或网络词；删除某个口语后事实和判断完全不变时，应直接删除。
- 不把 10 人团队、22—25 岁或 14% 变成没有来源的通用比例。
- 不因为终稿更顺，就跳过 GitHub 用途、亚马逊裁员因果和青年就业研究的最短限定。
- 不把「多来源自然交汇」理解成必须同时拼三条新闻；材料之间没有共同问题时，应拆题。

## 因果复盘

```text
日期和新闻概述先行
→ 读者看到一篇公司新闻通稿，尚不知道与自己有什么关系
→ 开头按来源重要性排序，没有先兑现标题里的读者问题
→ 先提出普通人会问的问题，在首屏补齐公司、事件和事实边界
→ 冷读者能同时复述「为什么点进来」和「具体发生了什么」
→ 适用于需要解释普通人为什么在意的公司新闻分析稿；短资讯可以事实先行
```

```text
亚马逊、GitHub、失业率各自形成一份小报告
→ 材料很多，但删掉小标题后不知道为什么从上一条走到下一条
→ 提纲按来源分类，既没有线性依赖，也没有统一比较尺度
→ 线性材料按读者下一问推进；平行证据围绕同一问题或尺度组织，并用场景把抽象机制落地
→ 隐藏小标题后，冷读仍能解释段落顺序或平行关系
→ 材料没有共同中间变量时拆题，不强求交汇
```

```text
等长段落、均匀口语和重复强对比一起制造「人味」
→ 表面热闹，语气仍像按模板调参
→ 在结构未稳定时做词级润色，把口语数量误当声音
→ 先修段落工作，再标语义转向、口语落点、框架词簇，并扫描是否存在不必要的强对比
→ 每个短句与口语都能说明自己的信息任务；删除后会损失具体判断或后果
→ 4—5 只适用于 APPSO 冷静分析型长文的编辑靶点，短讯、教程和来源原话不套用
```

```text
结尾完成标题回扣后又增加个人方法论
→ 末段出现第二个承诺，削弱「第二个人」的余味
→ 把结尾当成补充所有有用建议的容器
→ 只回答开头问题并增加一个读者后果；未在 brief 承诺的方法下沉或另稿处理
→ 删除末段任一建议后，标题承诺不会变弱；最后一句仍能单独表达全文判断
→ 方法稿和清单稿按 brief 兑现，不禁止行动建议
```
