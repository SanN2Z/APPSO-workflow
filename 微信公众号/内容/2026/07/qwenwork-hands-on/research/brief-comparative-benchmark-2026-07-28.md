# 千问办公横向体验稿 Brief

## 稿型

APPSO 风格的公众号体验分析稿。以统一任务横向测试千问办公、WorkBuddy 与 Codex，不做官网功能盘点，也不在结果出来前预设胜负。

## 读者问题

办公 Agent 已经不少，千问办公来得不算早。对已经用过 WorkBuddy、百度搭子、豆包或通用 Agent 的用户来说，为什么还要多装一个？它在哪类工作里能真正少一次搬运、少一轮返工？

## 暂定标题

办公 Agent 已经够多了，千问办公为什么还要再来一个？

结果出来后再判断是否改为带结论标题。

## 核心判断

千问办公没有独占「操作电脑」「远程下任务」「生成 Office 文件」或「发布网页」。它最值得测的是，能否把专业数据入口、可编辑交付物、网页发布和 IM／云端自动化接成一条更短的办公链路。

判断成败的单位不是功能数量，而是同一道任务中的可验收交付物与人工返工成本。

## 对照关系

- 千问办公：本次观察对象；
- WorkBuddy：较成熟的国产桌面办公 Agent 对照；
- Codex：通用 Agent 能力基线，用来区分「办公产品能力」与「通用工具调用能力」；
- WorkBuddy、DuMate、豆包、千问办公：作为任务中的国内市场研究对象。

## 统一任务

为编辑部选题会制作一份「国内 AI 办公 Agent 用户反馈与产品差异观察」，要求核查官方功能与价格，收集 32—40 条公开用户反馈，并交付：

1. `01_source_ledger.xlsx`
2. `02_findings.md`
3. `03_dashboard.html`
4. `04_run_log.md`
5. `05_metrics.json`
6. `06_dashboard_preview.png`

## 控制变量

- 第一轮均为 `native_default`；
- 使用默认或推荐模型；
- 不安装额外 Skill，不接自定义 API，不手动补数据源；
- 新建任务，使用相同 Prompt、时间窗口、交付格式和停止条件；
- 任务开始后不追加提示，仅进行必要的高风险操作确认；
- 记录时间、失败、重试、人工干预、来源有效性、事实错误、文件完整度和人工返工时间；
- Credits 只记录，不直接跨产品换算。

## 消融

第一轮完成后，仅千问办公增加一次 `official_enhanced`：打开官方小红书等数据能力，其余条件不变。

对比千问办公原生与增强两轮，判断差异来自 Agent 本身，还是官方数据源与工具，以及这些能力是否减少搜索、清洗和返工。

## 文章结构

1. 办公 Agent 已经拥挤，千问为什么还值得再测；
2. 千问可能的差异不在单个功能，而在整条交付链；
3. 三款 Agent 做同一道真实任务；
4. 第一轮不开 Skill，解释公平性和验收标准；
5. 三款原生模式结果；
6. 千问官方数据能力消融；
7. 结合完成质量、返工和使用边界给出适用人群判断。

## 写作要求

- 从场景和用户问题出发，不按官网菜单分节；
- 不把厂商功能描述写成作者体验；
- 只写真实发生的测试过程、失败和人工介入；
- 事实、厂商主张、测试结果和作者判断分开；
- 图片之间必须有承接文字，不做连续截图堆叠；
- 正文目标约 3000 字，结果部分优先，方法说明保持紧凑；
- 结果出来前不写「最好用」「更完整」「明显领先」等结论。
