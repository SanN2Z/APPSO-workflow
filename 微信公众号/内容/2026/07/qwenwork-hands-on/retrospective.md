## 因果复盘

```text
体验场景连续调整
→ 用户仍不认可交付形态，继续修改会浪费时间

→ 改为事实型功能指南
→ 用户进一步要求降低说明书感、加强公众号节奏

→ 检查正文无虚构体验，所有时效功能有官方来源
→ 本次格式选择仅适用于本稿，不推广为产品稿默认模板
```

## 2026-07-28 体验稿去横评与去参数化

### FB-018｜国内竞品不宜做公开胜负表

- source: user
- stage: structural_rewrite
- feedback: 千问办公与 WorkBuddy 等国内产品存在直接竞争关系，正文若按耗时、完成度和来源质量排出横向胜负，容易被双方理解为立场稿或黑稿；本文应以千问办公体验为主。
- harm: 主角被稀释，读者先看到输赢而不是产品对自己的用途；同时增加不必要的品牌关系风险。
- mechanism: 内部同题测试适合发现问题，不等于所有比较结果都适合公开做成排行榜。
- repair: 删除三方成绩表、竞品耗时图和逐项胜负总结；同类产品只保留为行业背景，正文只写千问办公的交互、产物、返工和待验证差异。
- verification: 正文不出现 WorkBuddy、Codex、DuMate 名称，不出现横向排名与综合推荐。
- disposition: case_only

### FB-019｜产品体验不能由秒数和样本数主导

- source: user
- stage: prose_and_evidence
- feedback: 普通用户不会首先关心任务精确跑了多少秒。评价应落在等待是否难熬、是否频繁打断、成品能否直接使用，以及哪些地方仍要人工收拾。
- harm: 参数把体验压成跑分，正文像实验报告，不像真实使用经验。
- mechanism: 研究阶段需要精确记录，公开写作只保留会改变购买或使用判断的数字。
- repair: 删除 Agent 自报耗时与界面耗时的技术支线及配图；将耗时改写为「等待体感」，把篇幅让给交互过程、成品可用性和返工成本。
- verification: 正文没有秒级横向计时，只以「四十多分钟」「不算快」说明本次等待感；核心段落均回答用户实际会遇到的动作与后果。
- disposition: watch
