# 千问办公场景体验稿 Brief

## 稿型

APPSO 公众号产品体验稿。以一次真实编辑部调研为主线，千问办公是唯一主角；同类产品只作为行业背景，不做国内办公 Agent 排名、逐项打分或胜负判断。

## 读者问题

办公 Agent 已经很多，千问办公还能替用户接走哪一段工作？它交来的东西能不能直接进入下一步，而不是停在聊天框里？

## 标题

千问办公体验：我把一项编辑部调研交给它以后

## 主判断

千问办公这次最有用的地方，是把搜索、制表、写作和网页生成收进同一个任务，最后交付一组可以继续修改的文件。它很会把零散资料包装成可展示的页面，但成品感不会自动解决来源分层：内部初稿可以省事，对外材料仍要明确限制官方来源、媒体消息和模型自创文案。官网宣传的 1688、小红书等专业数据入口是否能在真实账号里减少人工搬运，仍是下一轮最值得验证的差异。

## 体验主线

1. 从阿里 AI 战略、三条 Agent 产品线整合和 WorkBuddy 竞争背景切入，再问千问为什么值得多装一个；
2. 把一次编辑部调研完整交给它，不追加提示、不安装额外 Skill；
3. 等待不短，但任务不频繁要求人工接管；
4. 打开结果后，价值体现在 Excel、Markdown、HTML 和预览图已经各归其位；
5. 通过微信远程发起桌面任务，解释 IM 与本地客户端如何配合；
6. 让千问办公调查自己并生成网页，观察追问、执行、页面成品与事实边界；
7. 官网数据入口可能构成差异，但本次免费账号和默认模式没有跑通；
8. 以「Agent 能不能少一次数据搬运」的小观察和下一轮业务后台任务自然收束，不急于给生态能力下结论。

## 写作边界

- 不公开三方计时表、胜负表或综合排名；
- 不让秒数、样本数和文件数主导体验；
- 不讨论本次 Prompt 未严格定义的普通用户样本口径；
- 不把官网的数据接入主张写成当前免费账号已实测；
- 不把第三方 Skill 写成千问第一方入口；
- 不把任务启动截图写成文件整理结果已经成功；
- 不把一次任务外推为长期稳定性结论。

## 目标篇幅

正文约 2200—2800 字。场景先于功能，过程先于判断，功能名只在解释动作时出现。
