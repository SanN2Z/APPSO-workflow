# 公司飞书到公众号浏览器排版 SOP

## 1. 定位

这是 APPSO／爱范儿公司稿的浏览器排版执行通道。它在公司编辑确认飞书定稿后，把当前飞书文档转换为固定内联样式 HTML，直接覆盖微信公众号草稿并触发保存。

它只接管「排版与写入」，不替代：

- 选题、事实核查、逐句终校和编辑确认；
- 图片来源、权利与时效检查；
- 发布授权、群发与发布后复盘；
- 公司终稿与个人稿的隔离规则。

公司扩展不是仓库里的 `sealed_draft`。它依赖当前浏览器 DOM，会直接改写公众号草稿；每次执行仍属于需要当前任务明确授权的外部写操作。

- v1.10.0 源码目录：`tools/company/ifanr-feishu-wechat-layout/v1.10.0`
- Chrome 应加载目录：`D:\projects\自媒体运营\tools\company\ifanr-feishu-wechat-layout\v1.10.0\extension`
- 扩展版本：`1.10.0`
- `manifest.json` SHA-256：`AA4E61E879FDE34DDB09383F51AB0B99DB373BEACB89EEC456D4CFAF4F635396`
- 原始 22 文件树指纹：`50E9DE945BECBCAE5EAA1A068A4E3CEE63EB5CCAF3F983E40150877C07068862`

安装时在 `chrome://extensions` 打开开发者模式，选择「加载已解压的扩展程序」，加载上述 `extension` 目录。升级后必须重新记录扩展版本和 `manifest.json` 哈希，并重新做一次资格验证草稿。

源码和内嵌品牌素材按 `restricted`、`private-repository-only` 处理，只保存到当前私有知识库的 `tools/company/`，并只在授权公司环境内使用。根目录的用户原始交付包是本地归档副本，不是运行真源；不得把公司工具迁移到个人项目或公开仓库。

## 3. 架构与工作原理

```text
公司飞书 Wiki／Docx
  → 浏览器滚动全文并多轮确认 DOM 稳定
  → 抽取标题、段落、两级小标题、引用、列表与图片
  → 下载图片；超限静态图在浏览器内压缩
  → 生成固定内联样式 HTML 与 Base64 图片内容包
  → 暂存到 chrome.storage.local
  → 净空当前微信公众号正文编辑器
  → 写入标题、摘要、正文与图片
  → 等待微信把图片托管为平台地址
  → 自动保存
  → 人工重开草稿并验收
```

| 层 | 主要职责 | 关键实现 |
|---|---|---|
| Chrome MV3 壳层 | 页面权限、弹窗入口、状态与消息路由 | `manifest.json`、`popup.js`、`service-worker.js` |
| 飞书采集 | 最多 4 轮滚动扫描，只有 DOM 与页面高度稳定才接受 | `feishu-content-script.js` |
| 语义与版式 | 把飞书块归一为正文、两级标题、引用、列表、图片和横滑图库 | `feishu-page-reader.js` |
| 图片处理 | 使用当前飞书登录态下载；静态图超过 5 MB 时压缩；失败时原位留标记 | `static-image-compression.js` |
| 微信写入 | 清理危险 HTML，净空编辑器，填标题／摘要，等待图片托管并保存 | `editor-adapter.js`、`content-script.js` |
| 写入防护 | 阻止同时打开多个公众号编辑页，识别刷新、超时和保存状态 | `wechat-write-guard.js`、`page-state.js` |

浏览器直读失败后，扩展会尝试 `http://127.0.0.1:43127` 的本机增强服务。当前工具包没有附带该服务；不要下载或启动来源不明的替代程序。页面直读失败且公司未提供受控服务时，停止并走降级流程。

## 4. 公司浏览器版式合同

用户于 2026 年 7 月 23 日确认：公司稿使用公司扩展自身格式。该通道的运行时样式以扩展精确版本为真源，不再用仓库的 `appsso-article-v1.css` 覆盖。

v1.10.0 当前合同：

- 飞书中出现的第一种标题层级映射为 22 px 橙色标题；
- 第二种标题层级映射为 18 px 橙色标题；
- 正文为 15 px，左右块级边距各 16 px，行高 `1.8`；
- 引用为 15 px 灰字和 3 px 灰色左边线；
- 相邻 2 张及以上图片自动组成横向滑动图库；
- 正文第一张图由扩展插入公司题图。

这套合同只适用于 `company_browser` 执行通道。仓库内 `appsso-article-v1` 仍是本地密封草稿的独立回退 profile，两者不要求数值一致，也不能混合进同一次交付。

## 5. 执行前门禁

只有同时满足以下条件，才可以进入扩展：

1. 当前任务明确允许创建或覆盖 1 个公众号草稿；没有授权时只做架构检查和本地准备。
2. 飞书文档是公司编辑确认的本轮定稿，标题、正文、图片顺序和图注已经锁定。
3. 公司终稿若属于 `restricted`，不为方便排版而复制进公开或个人仓库；知识库只保存允许入库的工作稿、脱敏 diff 与复盘。
4. 所有外部事实、引语、数字和图片权利已经完成相应检查；扩展的「读取成功」不代表这些门禁通过。
5. 如果仓库内容包就是 APPSO 生产包，`publish.yml` 必须声明 `project_adapter: "appsso"`；如果公司定稿只在受限飞书中，旧内容包仅提供用户明确允许复用的图片，则把旧包记为 `asset_donor`，保留其原品牌字段、生图计划和 preflight receipt，并在 `publish-record.md` 另记 `handoff_brand: "AppSo"`。不得为迁移而改写历史生成凭据。
6. 飞书正文不含待保真的表格、附件、嵌入卡片、复杂代码块或其他特殊块。必须保留时改走人工交接。
7. APPSO 稿在扩展中手动选择 `AppSo`，不使用「自动」猜品牌。
8. 飞书正文开头不重复放置扩展会自动插入的 APPSO 题图。
9. 只保留 1 个微信公众号图文编辑页；首次使用新版本时只写空白资格验证草稿。

## 6. 操作流程

1. 使用公司专用 Chrome Profile 登录飞书与微信公众号。
2. 打开编辑确认的飞书 Wiki／Docx，等待正文和图片完全加载。
3. 打开扩展，把「文章题图」明确设为 `AppSo`，静态图画质默认选「高清」。
4. 点击「收录当前飞书文档」，等待状态变为「已就绪」。
5. 核对内容块、图片数量、题图品牌和特殊块／问题图片提示。
6. 打开唯一的目标公众号草稿。首次验收或目标不确定时，必须使用空白测试草稿。
7. 再次核对账号、目标草稿和飞书文档；获得本次外部写入授权后，点击一键覆盖并排版。
8. 等待微信显示保存结果。出现「需检查」、样式旁路、标题／摘要未确认、图片占位或保存未确认时，一律按失败处理，不直接重试。
9. 人工检查标题、摘要、正文、两级小标题、引用、列表、题图、普通图片、图注和图片顺序。
10. 补充封面、作者、原文链接和经授权且仍有效的尾图；扩展不会完整处理这些字段。
11. 保存后刷新或关闭重开草稿，再做一次手机预览与结构检查。
12. 在 `publish-record.md` 记录工具版本、飞书定稿标识、目标草稿、检查结果和异常。
13. 回到飞书页打开扩展，点击「清除」，删除 `chrome.storage.local` 中暂存的主要全文与 Base64 图片。v1.10.0 的 `ifanrWechatPageStatus` 可能仍保留草稿 ID 或标题；处理敏感稿、离开共享设备或停用专用 Profile 前，还要在扩展调试页清空该扩展的本地存储。

## 7. 硬失败与重试

以下任一情况出现，都不能把本轮写入记为成功：

- `styleValidationBypassed: true` 或 `layoutStyleConfirmed: false`；
- `metadataConfirmed: false`，或标题／摘要发生截断；
- 仍有图片补位标记、图片托管失败或图片顺序不一致；
- 特殊块被压平后改变含义；
- 保存状态未确认；
- 保存后重开出现字号、间距、引用、图库或图片丢失；
- 技术详情显示的来源文档不是本轮目标飞书；
- 当前公众号账号或草稿目标不确定。

扩展可能已经部分写入并自动保存。失败后先检查当前草稿，不得连续点击重试。确认草稿状态后，再选择：

- 修复飞书内容并重新收录；
- 新建空白草稿后重试；
- 回退到仓库 `manual_editor` 版本化交接；
- 仅需交付固定 300 px 高的连续图片纵向滑动组件时，按 [`wechat-publishing.md` 的离线纵向滑动合同](<../../.agents/skills/self-media-ops/references/wechat-publishing.md#纵向滑动长图组件离线交接>) 使用统一 `scroll-handoff` 命令；
- 在另行明确授权且主题已取得资格时，使用 `sealed_draft`。

## 8. 验收矩阵

扩展每次升级至少覆盖：

| 用例 | 必查结果 |
|---|---|
| 普通长文 | 标题、摘要、正文完整；保存后重开不丢格式 |
| 一种飞书标题层级 | 全部映射为 22 px，不意外降为正文 |
| 两种飞书标题层级 | 分别映射为 22 px 与 18 px |
| 引用与列表 | 不重复、不丢文字；列表顺序正确 |
| 连续图片 | 横滑图库在保存后仍可用，图序正确 |
| 超过 5 MB 的静态图 | 压缩后可读，无色彩或透明通道灾难 |
| GIF | 微信托管完成；失败时原位明确标记 |
| 标题／摘要接近上限 | 没有静默截断 |
| 写入失败 | 不误判成功；先检查已自动保存的部分结果 |
| 缓存清理 | 清除后不再保留上一次全文、图片内容包、草稿 ID 或标题；v1.10.0 需额外复核 `ifanrWechatPageStatus` |

首次真实后台往返通过前，v1.10.0 的「格式来源」已经按用户决定启用，但「生产运行资格」仍记为待验收。本地直接调用扩展 `buildFixture` 生成预演稿，只能证明排版器、正文保真和本地图片输入可工作，不能替代飞书 DOM 抓取、微信编辑器写入、图片托管、自动保存和重开检查。通过后把精确公众号账号、扩展版本、Chrome 版本和验收日期写回版式证据文档。

## 9. 保密与反馈

- 扩展未发现第三方遥测、远程脚本或硬编码凭据；网络范围主要是飞书、微信公众号和本机回退服务。
- 全文、飞书 URL 与 Base64 图片会保存在 Chrome 本地存储，使用结束必须手动清除。
- v1.10.0 的「清除」不会完整覆盖 `ifanrWechatPageStatus`；在修复并完成回归前，公司专用 Chrome Profile 与额外本地存储清理仍是硬要求。
- 「查看技术详情」可能包含飞书 URL、稿件标题和小标题。提交反馈前先脱敏，不向外部渠道发送完整详情。
- 不提交 Cookie、Token、密码、AppSecret、登录态或完整请求头。
- 公司扩展与内嵌品牌素材只用于获授权的公司账号；源码只进入当前私有仓库的版本化工具目录，不迁移到个人稿、个人项目或公开仓库。
